# REYTER на Next.js

Переписування сайту й адмінки з ванільного JavaScript на Next.js.
Поки триває, робочий магазин лишається на місці:

| Що                | Де зараз                  |
| ----------------- | ------------------------- |
| Старий сайт       | `reyter.men/`             |
| Чинний новий сайт | `reyter.men/new/`         |
| Адмінка           | `admin.reyter.men/`       |
| **Ця версія**     | ще не опублікована        |

## Чому саме так

**Дані читаються без Firebase Admin SDK.** Правила бази дозволяють
публічне читання опублікованого каталогу (`published/catalog`) і
залишків (`inventory`) — тому сервер бере їх звичайним REST-запитом
(`lib/firestore.ts`). Ні службового акаунта, ні Node-only залежностей:
сторінки рендеряться будь-де, зокрема на Cloudflare.

**Стилі перенесені як є.** `styles/` — це копія `new/css/`. Дизайн
уже вивірений, переписувати його на щось інше означало б зламати
те, що працює, заради самого переписування.

**Логіка каталогу — чисті функції.** `lib/catalog.ts` не знає ні про
DOM, ні про мережу, тож однаково працює на сервері й у браузері.
Це порт `new/js/catalog.js` один в один.

**Кошик живе поза React.** `lib/cart.ts` пише в localStorage і
будить підписників; React читає його через `useSyncExternalStore`.
Тому кошик доступний із будь-якого коду, а не лише з дерева
компонентів, і всі, хто його показує (бейдж, панель, картка
товару), не можуть розʼїхатись.

## Перевірки

Три, і всі — на справжніх даних.

**Відповідність каталогу.** `tools/parity.ts` бере опублікований
каталог, проганяє через нього стару логіку (`new/js/catalog.js`)
і нову (`lib/catalog.ts`) і порівнює результат по кожному товару.
Поки два сайти живуть паралельно, вони мусять однаково рахувати
наявність, розміри, комплекти й кольори.

**Складання замовлення.** `tools/order-check.ts` збирає замовлення
з реального каталогу так само, як сторінка оформлення, і звіряє
результат — нічого нікуди не пишучи. Головне, що він стереже:
у замовленні лежать назви й категорії, а не самі артикули, тож
лист покупцю не зіпсується, коли каталог зміниться.

```bash
node --experimental-strip-types --import ./tools/ts-resolve-register.mjs tools/parity.ts
node --experimental-strip-types --import ./tools/ts-resolve-register.mjs tools/order-check.ts
node --experimental-strip-types --import ./tools/ts-resolve-register.mjs tools/account-check.ts
```

**Прогін у браузері.** `tools/cart-e2e.mjs` і `tools/sets-e2e.mjs`
відкривають зібраний сайт у справжньому Chrome і проходять шлях
покупця: додати товар, переспитати каталог, відкрити панель,
дійти до оформлення, знайти місто й відділення Нової Пошти.
Залежностей не потребують — лише встановлений Chrome.

```bash
npm run build && npm start &
node tools/cart-e2e.mjs http://localhost:3000
node tools/sets-e2e.mjs http://localhost:3000
node tools/account-e2e.mjs http://localhost:3000
```

**Кабінет і відстеження.** `tools/account-check.ts` перевіряє
крокомір, повторення замовлення й — найважливіше — що ключ
відстеження збігається символ у символ з тим, який рахував старий
сайт. Розбіжність там означала б, що покупці зі старими
замовленнями втратять до них доступ.

Окремо він стежить, щоб у публічний запис `tracking/{key}` не
потрапили імʼя, телефон, пошта й точна адреса: цей документ
читає будь-хто, хто знає ключ.

## Що вже є

**Каталог**

- каталог із категоріями, рендериться на сервері
- сторінка товару за власною адресою `/p/{артикул}` — 36 сторінок
  генеруються наперед як статичний HTML
- метадані для соцмереж і `og:image` на кожен товар
- розмітка Schema.org Product із реальною наявністю
- комплекти: розмірна сітка кожного складника

**Кошик і оформлення**

- вибір розміру й додавання в кошик — єдиний інтерактивний
  острівець на сторінці товару, решта лишається статичним HTML
- комплекти збираються за розміром кожного складника
- панель кошика з категоріями, складом комплекту й кількістю
- промокоди: умови завжди перечитуються з бази, у сховищі лежить
  лише сам код
- доставка: Нова Пошта з пошуком міста й відділення, закордон —
  окрема форма з перевіркою індексу та штату
- підтвердження замовлення дзвінком або в месенджері
- замовлення йде в базу, а звідти — в Telegram і листом покупцю

**Кабінет**

- вкладка живе в адресі (`/account?tab=orders`), тож посилання
  на «мої замовлення» можна надіслати, а «назад» працює
- вхід через Google або пошту, відновлення пароля
- профіль синхронізується з хмарою: заповнене на одному пристрої
  видно на іншому
- адресна книга: замовляють собі, на роботу, рідним
- історія замовлень зі статусом і крокоміром доставки; коли база
  не відповідає — локальна копія й чесна про це примітка
- повторення замовлення з тими самими розмірами складників
- персональні знижки з умовами людською мовою
- відстеження без акаунта за номером і телефоном — окремою
  адресою `/track`, яку можна покласти в лист
