# Викладка на Cloudflare

Сайт зібраний Next.js, тож це **Worker**, а не тека з файлами.
Сторінки товарів статичні, але каталог перечитується раз на
хвилину — саме тому потрібен воркер: публікація з адмінки
доходить до покупця сама, без перезбірки.

```bash
cd app
npm run cf:preview   # локально, рівно як у Cloudflare
npm run cf:deploy    # викласти
```

`npm run cf:preview` піднімає той самий воркер у себе. Перевіряти
краще саме ним, а не `npm start`: `next start` — це Node, а в
Cloudflare інше середовище, і різниця вже раз вилізла (див.
`next.config.ts`, чому Firebase береться браузерною збіркою).

## Порядок переходу

Робити по одному кроку й перевіряти між ними. Кожен крок
відкочується поверненням домену на попереднє місце.

**1. Викласти воркер, нікуди не перемикаючи.**

```bash
cd app && npm run cf:deploy
```

Cloudflare дасть адресу `reyter.<акаунт>.workers.dev`. Відкрити її
й перевірити: каталог, картка товару, кошик, оформлення, кабінет.
Магазин на `reyter.men` при цьому не змінюється — він і далі
роздається старим проєктом Pages.

**2. Додати домени у Firebase.**

Firebase Console → Authentication → Settings → Authorized domains →
додати `reyter.<акаунт>.workers.dev`. Без цього вхід через Google
не спрацює й адмінка не відкриється.

**3. Перевірити адмінку на тестовій адресі.**

Маршрутизація за доменом уже в коді (`app/middleware.ts`):

- `admin.*` → адмінка з кореня, адреса в браузері не міняється;
- `/admin` на магазинному домені → перенаправлення на `admin.`

Щоб перевірити її наживо, у Cloudflare → Workers & Pages → `reyter`
→ Settings → Domains & Routes додати `next.reyter.men` і
`admin-next.reyter.men`.

**4. Перемкнути адмінку.**

Прибрати `admin.reyter.men` зі старого проєкту Pages й додати
до воркера. Магазин ще на старому.

**5. Перемкнути магазин.**

Так само з `reyter.men` і `www.reyter.men`.

Старий проєкт Pages не видаляти щонайменше тиждень: повернути
домен назад — це одна дія в панелі.

## Що зробити руками, окремо від викладки

**Правила бази.** `new/firestore.rules` посилено — тепер сервер
перевіряє строки дії промокоду, мінімальну суму, набір полів
замовлення й те, що залогінений покупець не вкаже чужу пошту.
Firebase Console → Firestore Database → Rules → замінити все
вмістом файлу → Publish.

Те саме для `new/storage.rules` (Storage → Rules).

**Змінна ALLOW_ORIGIN у воркері сповіщень.** Якщо магазин
переїде на нову адресу, дописати її туди через кому — інакше
браузер не пустить запит на відправку замовлення.

## Що лишається на старому місці

Старий сайт у корені репозиторію (`index.html`, `new/`) нікуди не
дівається: він і далі збирається тим самим проєктом Pages. Поки
домени на нього не вказують, він просто лежить — але data.js із
нього читає резервна копія після публікації, тож видаляти його
не варто.
